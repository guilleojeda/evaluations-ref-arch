# Operations agent

This document describes the initial live S0 investigation and the later evaluation capabilities that build on it. Phase 4 adds the genuine alarm-to-AgentCore path; S1–S5 remain the separate evaluation progression. See the [reference overview](../../README.md) and the [public talk plan](../talk-plan.md).

## Purpose and boundaries

The operations agent performs one bounded investigation in response to one genuine application alarm event, then returns one report. It does not conduct a follow-up chat. A dashboard poll, an alarm that is already active, incident activation, a configuration action, or recovery does not itself invoke the agent. A run must retain the identity of the originating alarm event so its trace and report can be matched to that event.

The live baseline uses that genuine alarm path. Planned regression executions retain their case and originating-event provenance; they are not live alarm deliveries and do not use live event deduplication as their execution identity. Regression/replay execution is a later evaluation capability, not part of the Phase 4 live Runtime. The controller has no manual agent trigger, and replay must not be presented as a new live investigation.

The run input identifies the affected service and scope, the originating alarm/event and its time, the reported symptoms, and when investigation began. Regression input also supplies the case's effective investigation reference time. Trusted deployment configuration identifies the permitted evidence sources. A CloudWatch alarm invokes a small Lambda adapter directly on a transition to ALARM ([CloudWatch alarm actions](https://docs.aws.amazon.com/AmazonCloudWatch/latest/monitoring/alarms-and-actions-Lambda.html)).

The canonical live event identity is the alarm ARN plus the UTC-normalized ALARM state-transition timestamp from the delivered `alarmData.state.timestamp`. The adapter validates the actual CloudWatch event, selected alarm, account, Region, and ALARM state, then forwards the verbatim event and the checked release's deployment identity to AgentCore Runtime with bounded native Lambda delivery retries. The adapter does not create or own a run record. Runtime conditionally creates the single `running` row keyed by alarm ARN and normalized transition time. Only the handler that confirms its insert may start the investigation; a duplicate, conditional conflict, or uncertain insert acknowledgement cannot start another one, including when Lambda retries a lost response. There is no claim reclaim, manual live trigger, or synthesized event. `DescribeAlarms.StateTransitionedTimestamp`, `StateUpdatedTimestamp`, and read time are observations, not substitutes for the transition timestamp in the delivered event.

Retain the originating identity after the alarm returns to OK, and make durable runs discoverable by alarm and originating transition across missed polls or a controller restart. Do not synthesize an event or timestamp to fill a gap. The run table uses the alarm ARN as its partition key and the normalized transition timestamp as its sort key; exact reads and bounded recent-run queries use the base table.

The alarm covers the whole API stage. The agent must locate the affected operation rather than assume that every event means checkout is failing.

The adapter invokes the pinned Python agent endpoint on AgentCore Runtime in `us-east-1` using IAM authentication. Each accepted transition uses the native Runtime session from the invocation context and one Strands agent, with no follow-up chat or AgentCore Memory. The Runtime wrapper writes orchestration state: it conditionally creates `running`, then persists `complete` with one validated structured report or `failed` with a known terminal failure. A stranded `running` row remains overdue/incomplete and is not reclaimed or run a second time. Model-facing tools remain read-only and cannot write application or controller state.

The run record retains the exact originating CloudWatch event, normalized alarm transition, run and native session identities, candidate and prompt digest, model/profile, final Runtime ARN/version, endpoint, source revision, release artifact SHA-256, lifecycle status and timestamps, report or known failure, trace reference, and sanitized source-capture reference. The `deployment` attestation is supplied by the checked release after MMDSv2 and the final endpoint version are read back; it contains `runtimeArn`, `runtimeVersion`, `endpointName`, `sourceRevision`, and `artifactSha256`. The package records its own source and prompt hashes; it cannot contain a self-hash of the complete ZIP. The controller discovers these durable records independently of alarm state and the adapter's invocation response, including after missed polling or restart. A lost connection does not overwrite a Runtime-written terminal result or establish that the investigation failed.

The Python agent calls AWS read APIs directly in live investigations; AgentCore Gateway is not selected. Its four focused tools use trusted application/deployment sources and enforce finite query and run bounds.

### First-time model access before live rehearsal

The live profile is `us.anthropic.claude-sonnet-4-6`, backed by model ID
`anthropic.claude-sonnet-4-6`. Before a live rehearsal, the account
administrator completes Anthropic's first-time-use form and verifies the
account use case and model availability as described in the
[bootstrap handoff](../../infrastructure/bootstrap/README.md#before-the-first-live-anthropic-runtime-rehearsal).
A prior successful `Converse` call can be temporary and does not prove these
checks passed. If agreement availability remains `NOT_AVAILABLE`, inspect the
offer and terms separately before authorized acceptance. The current release
workflow does not automate this account onboarding.

The planned local and CI regression path will use the same tools backed only by versioned, queryable captured evidence, coherent at the case's explicit effective investigation reference time. Its provider must not fall back to current AWS state or evidence from after that time. Logs and metrics retain their query windows, configuration is read as of the reference time, and bounded change history is limited to changes effective by then. Source observation time, capture time, and the case reference time remain distinct; an as-of value must be supported by captured observations or history, not invented. Relative query windows, freshness, and current-state assessment use the case reference time; real execution timestamps remain separate provenance. Freshness, partial results, and unavailable evidence remain visible to the agent. The [evaluation contract](../evaluations.md#captured-evidence-for-regressions) owns capture review and versioning; exact file/schema/provider choices remain open.

The model chooses which tools to call, their query windows and filters, their order, and whether further evidence is needed. It receives alarm context and source configuration rather than a prepared evidence bundle or fixed investigation sequence. Equivalent supported investigations are acceptable.

| Tool responsibility | Evidence returned |
| --- | --- |
| `search_logs` | Search Gateway, checkout, and inventory logs by service, time, operation, or error, and correlate available request or invocation IDs. |
| `read_metrics` | Read request outcomes, latency, dependency timing, and Lambda metrics for relevant functions and windows. |
| `read_configuration` | Read sanitized current values in live investigations. The planned captured-evidence regression provider will resolve values as of the case reference time, including actual numeric versions/aliases, revision identifiers, reserved-concurrency caps, memory allocations, the Inventory execution role, and the exact Deny policy/default document and access state. |
| `read_change_history` | Read relevant ordinary changes and timestamps for those configuration values. |

Results identify source, scope, query window, observation time, freshness, completeness, and truncation or failure. Current selected values may be visible even when they match a baseline, but controller baseline mappings, private incident labels, credentials, raw authentication configuration, code contents, and mutation/reset permissions are excluded. The agent does not directly inspect Orders or Inventory business tables for integrity: it reports business impact only when supported by operational evidence, with no direct-data tools added to the baseline. The initial candidate uses `us.anthropic.claude-sonnet-4-6`; each investigation has a 240-second deadline with cancellation, at most 12 outbound model requests (including structured-output fallback requests) and 12 tool calls, a 30-minute per-query lookback, bounded source pages, and model-facing results capped below 12 KiB. These are implementation limits, not measured latency or a promise that every run produces a report. A run still `running` at the deadline remains incomplete and is shown as overdue after its deadline.

The hosted controller reads run records through its authenticated investigation-discovery endpoint independently of the alarm-state endpoint. It polls each source separately every five seconds, retains the last good value on read failure, and marks it stale after two intervals. An exact alarm ARN and transition query returns only the matching run or no run; default discovery returns a bounded recent list for the configured current alarm. A running row past its deadline is overdue/incomplete, distinct from a completed report whose assessment is `unknown`. There is no hidden manual agent trigger. The record identifies the prompt digest, model, endpoint, Runtime version and checked release for that run.

## Report contract

Each report gives one current assessment and one recommendation. It distinguishes observed facts from diagnoses and hypotheses, cites the source and time window for material evidence, states uncertainty and plausible alternatives, and includes failed or unavailable queries where they affect the conclusion. The structured report contains `assessment`, `summary`, `recommendation`, nonempty `evidence` citations, `uncertainties`, and `alternatives`. A supported recommendation names its target and value/unit or provides the policy detail needed to act. Each citation identifies `source`, `resource`, `windowStart`, `windowEnd`, `observedAt`, and `finding`. Strands returns the report through structured output validated by a Pydantic model. Explain confidence through supporting observations and material gaps rather than an invented probability. [Strands structured output](https://strandsagents.com/docs/user-guide/sdk/agents/structured-output/).

The current-scope state is one of:

| State | Meaning |
| --- | --- |
| `ongoing` | Current evidence supports that the reported service problem is still present in the investigated scope. |
| `recovered` | Fresh evidence supports that the reported problem has stopped in the investigated scope. A quiet period or successful configuration readback alone is insufficient. |
| `unknown` | Evidence is missing, stale, conflicting, or too narrow to establish whether the problem is ongoing or recovered. |

The state describes the service evidence, not whether a proposed controller action completed. In particular, configuration acknowledgement or readback does not establish incident recovery. An unknown state can be the correct result of a completed investigation.

The report contains exactly one recommendation using one of these labels:

| Label | Meaning and required detail |
| --- | --- |
| `Increase reserved concurrency` | Identify `checkout` or `inventory`, the observed constrained function, and a selected higher cap grounded in relevant evidence. Do not invent a numeric target or claim the cap will work without separately observing traffic. |
| `Increase memory` | Identify `checkout` or `inventory` and a selected larger memory allocation in MB grounded in relevant evidence. This is a supported controller action, but it is not an accepted recommendation for the selected cases; memory cannot remove the Inventory role's explicit Deny. |
| `Restore inventory access` | When a required read is denied, ground the recommendation in the correlated denied read and the observed Inventory alias/version, execution role, and exact policy. Recommend selecting the healthy role-backed version at the current memory. Do not recommend broadening or mutating the inventory role. |
| `Other` | Explain the other response, why no remediation is needed, or why evidence is insufficient for a supported action. Use this for a supported no-action conclusion on a recovered incident, or a qualified/abstaining answer when state or cause is unknown. |

The displayed labels are the recommendation choices. A supported recommendation names its target and value or expected policy; `Restore inventory access` must identify the healthy role-backed version at current memory in its value/detail, and `Other` must contain a nonempty explanation. If evidence does not support a target or value, the agent uses `Other` and explains the limitation rather than fabricating one. The presenter independently decides whether to use a controller shortcut. The agent never calls the controller or claims that it applied a change.

Keep three outcomes distinct:

- **Run completed:** the bounded investigation produced a report. It may still report state `unknown` because task evidence is uncertain.
- **Task uncertain:** the report is complete but identifies missing, stale, conflicting, or insufficient evidence; this is a report conclusion, not an execution failure.
- **Run failed or incomplete:** the investigation or report could not finish, such as when the matching event cannot be established or a required operation is interrupted. Preserve the failure and partial trace; do not turn it into a completed `unknown` report or a pass.

Capture the actual model calls, tool calls and results, query windows, structured report, and correlated run/event identity through AgentCore observability from S0. These traces document captured agent activity; they are not evaluation scores. The application telemetry remains the evidence for diagnosis, while the trace is evidence of agent behavior. AgentCore Evaluations remains a later-stage capability as described below.

Retain sanitized source captures needed for later queryable cases alongside that trace, including incident-time configuration before recovery changes it. Runtime writes them under the private evidence bucket's `agent-source/` prefix, separate from controller checkpoint and journal data. The durable capture reference identifies the bucket/prefix and baseline/manifest/query-result keys, covered source interval, actual configuration observation time, per-source coverage/completeness, and explicit gaps; later query-result persistence merges into the reference without dropping baseline metadata. Source capture is separate from the model's investigation and imposes no mandatory tool order. This is raw evidence recording at S0; case review and captured-evidence regression execution begin at S1 or later.

Verify trace capture through the actual alarm-to-Lambda-to-Runtime path. AWS documents that an unsampled Lambda trace context can suppress Runtime spans; configuring observability alone does not establish that the required investigation was captured. See [Lambda-to-Runtime tracing](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-troubleshooting.html#runtime-troubleshooting-lambda-spans).

## Selected incidents and expected recommendations

Both selected incidents use unchanged healthy application code and can return the same dependency-failure 502 before checkout starts a transaction. The [scenario contracts](../demo-scenarios.md) define activation and application observations; the [application design](application.md#operational-evidence) defines the available telemetry.

| Condition | Evidence the agent should assess | Correct recommendation |
| --- | --- | --- |
| Inventory capacity overload | Actual inventory throttles and invocation evidence, current positive cap, relevant demand and request windows, and evidence ruling out a checkout/Gateway bottleneck. Distinguish concurrent-execution exhaustion from the synchronous Invoke request-rate limit when the records support it. Rejected invokes do not execute inventory code or count as its invocations/errors. | `Increase reserved concurrency` for `inventory`, with a selected higher cap supported by the observed demand and current configuration. |
| Inventory access denied | Correlated failed inventory read plus the current Inventory alias/version, execution role, exact Deny policy/default document, and relevant deployment/change history. The inventory role's required read is denied; missing child logs alone are not proof. | `Restore inventory access` by selecting the healthy role-backed version at the current memory. |
| Recovered service with a stale alarm | The originating incident and alarm times plus fresh post-action application evidence in the investigation window. Distinguish ongoing symptoms from historical evidence; ordinary traffic success does not establish that a previous capacity surge now succeeds. | `Other`, with a no-remediation explanation if recovery is supported, or a qualified/insufficient-evidence explanation if it is not. |

For the overload case, increasing checkout capacity is the wrong target while inventory remains constrained. For access denial, neither concurrency nor memory removes the denied version's explicit Deny. A memory action is a real qualified-version/alias allocation change that preserves the current access state, but is not the accepted remedy for either selected case. The [scenario contracts](../demo-scenarios.md) define the workload comparisons that establish action effects; the [failure controller](failure-controller.md) defines execution and observation boundaries.

The agent does not see private scenario labels, expected answers, intended causes, controller baseline values/mappings, credentials, or raw authentication configuration. It may see the actual sanitized current cap, memory setting, Inventory alias/version/role/policy state, relevant qualified configuration and ordinary management history even when a current value happens to match a baseline. A deployment or revision can be a candidate explanation, not proof of causality. Missing, failed, or stale evidence remains visible; absence of evidence is not evidence of health.

## Instruction versions

Keep one shared instruction body and a versioned recommendation rule. The shared body describes the bounded investigation, the four read-only tools, source and time-window citations, the structured report, and the distinction between ongoing, recovered, and unknown state. It keeps expected answers and private controller information out of agent input and makes clear that the agent proposes a response without executing it. Model, tool contracts, permissions, and report schema stay fixed across the three candidates.

The Phase 4 Runtime packages the shared instruction and the faulty recommendation rule as its initial S0 candidate. That rule deliberately favors more Inventory memory after dependency failures. The actual alarm-triggered report and prompt digest establish what ran; wording alone is not evidence that the model made the faulty recommendation. The repaired and regressed rules below belong to later evaluation stages.

| Candidate | Recommendation rule | Intended behavior to verify |
| --- | --- | --- |
| **Faulty**, used at S0–S2 and retained for comparison | “When inventory dependency requests fail, recommend increasing inventory memory as the first remediation.” | During the denied-read incident, the agent investigates but recommends `Increase memory` for `inventory`. A supported larger MB value does not make that action correct. This faulty preference is the instruction defect being tested. |
| **Repaired**, introduced at S3 and carried through S5 | Replace the faulty rule with: “Choose a response that addresses the failure mechanism supported by the evidence. Do not substitute a resource increase for an unrelated failure. If fresh evidence supports recovery, recommend no configuration change. If the cause or target is unsupported, use Other and explain the missing evidence.” | Recommend `Restore inventory access` for the denied read, grounded in the alias/version/role/policy and failed read, with the concrete target being the healthy role-backed version at the current memory; recommend an evidence-supported Inventory cap increase for the capacity case. Use `Other` appropriately for recovery or insufficient evidence. Evaluate all reviewed cases; the prompt edit alone establishes no improvement. |
| **Regressed**, submitted to the existing gate at S5 | Replace the repaired rule with the faulty memory-first rule again. Leave the shared instructions and all other candidate settings unchanged. | Reintroduce the denied-read recommendation defect. The existing action-correctness check for that case rejects `Increase memory`; cases, evaluators, and release policy are unchanged. The repaired deployed candidate remains in place. |

This makes both live prompt edits small and attributable: first replace the faulty preference with evidence-based selection, then restore that preference in a new candidate to demonstrate a regression. Keep the faulty and regressed candidate identities distinct even if their instruction text matches. Neither candidate may bypass the actual investigation or replace the displayed output. Retain fresh candidate traces, reports, and per-case findings to establish the intended failure and repair; do not present these planned outcomes as collected results.

The [worked denied-read case](../evaluations.md#worked-case-inventory-access-denied) connects these instructions to the evidence, expected recommendation, action check, and semantic criterion. It is the failure witness for the prepared S5 regression; additional candidate variants are optional.

## Software stages

The [demo progression](../demo-progression.md) defines the six capability checkpoints. The checkpoints add evaluation capabilities and candidate versions; they do not silently change incident, case, or provider meaning. The same known-defective candidate remains available from S0 through S2 and for comparison after the prompt-only repair at S3. The repaired candidate continues through the S4 developer experiment and S5 release gate.

| Stage | Agent behavior and expected result |
| --- | --- |
| **S0 — Instrumented agent** | Run one genuine alarm-triggered bounded investigation with the faulty instruction version and retain the actual tool outputs, report, trace, and sanitized source capture. There are no evaluation cases, evaluators, scores, or gate. Its selected defect is `Increase memory` for `inventory` during access denial, with a larger MB target grounded in the observed setting. This is incorrect because memory does not remove the policy denial. The report must come from the genuine investigation and evidence. |
| **S1 — Agent with reviewed cases** | Keep the unchanged faulty candidate. Review the input and captured-evidence reference as a repeatable case, define acceptable and unacceptable behavior, fully construct one case, then open the separately prepared case file. Require `Restore inventory access` for the denied read, record the capacity case's expected inventory-cap increase, and allow valid `Other` outcomes for recovered or insufficient evidence. There is no score or pass/fail verdict yet. |
| **S2 — Evaluated agent** | Keep the same faulty candidate. Add deterministic checks for recommendation, target, numeric value, report fields, and case-specific trace facts, plus semantic diagnosis and grounding criteria with the configured judge. Introduce both evaluator types here and show AgentCore evaluation results. Checks allow equivalent evidence-query sequences and do not demand a fixed tool order; the candidate remains faulty through S2. |
| **S3 — Repaired candidate** | Replace the recommendation rule only. Execute the fresh candidate through the prepared local runner using captured providers, then score its actual execution and compare it with the original on the same cases and criteria. The [S3 evaluation path](../evaluations.md#s3-fresh-candidate-before-deployment) owns the execution and scoring steps. A pending result remains pending. |
| **S4 — Agent with developer experiment workflow** | Keep the same repaired candidate. Use the local Strands experiment entrypoint to connect the case, task, evaluator, report, and comparison, and evaluate the existing reviewed local release policy before the first deployment. Deployment is an action, not another stage. |
| **S5 — Agent with release gate** | Keep the repaired candidate deployed. CI runs the same experiment and policy before deployment. Failed or incomplete required results block deployment. Submit the regressed instruction version and show the existing denied-read action check reject its memory recommendation; there is no S6. |

S1 review defines acceptable behavior from evidence and scenario contracts; the faulty response is evidence of a defect, not the definition of success. Regression runs let each candidate choose its own tool queries, windows, and order; they do not replay a recorded call sequence, inject labels or expected answers, or replace candidate outputs. A fixed captured trace may be judged again, but cannot establish that a changed candidate executed. Each regression execution has its own identity, separate from the live event-deduplication identity, while retaining the original case and event provenance. A corrected recommendation does not prove that a controller action was applied or that the application recovered. Evaluation scores the investigation and report, not service health or remediation success.

The initial defect and its repair belong to identifiable versions of the agent's instructions. The selected candidate must actually produce its report through an investigation; replacing the recommendation in a displayed report is not a candidate execution. Runtime and evaluation use one agent constructor, with tools backed by the approved live or captured providers; this does not introduce a second agent architecture. Their exact implementation and repeatability remain to be established.

## Evaluation and remaining decisions

Use [evaluation approach](../evaluations.md) for case review, evaluator roles, release policy, and measurement limits. Strands supports repeatable regression experiments around the candidate. AgentCore Evaluations assesses actual instrumented traces; a Strands report is not itself an AgentCore result. The intended progression starts trace and source capture at S0, adds reviewed cases at S1, introduces deterministic and semantic evaluation at S2, repairs only the prompt and compares a fresh candidate at S3, connects the full local Strands experiment at S4, and automates the same experiment and policy in CI at S5. Do not evaluate every check twice merely to demonstrate both products.

Evaluations assess agent behavior, not whether the application is healthy. An agent can diagnose an outage correctly while the service remains broken; a passing case does not establish recovery or production safety. Keep incomplete, failed, or pending required evaluation work from appearing as a pass. The selected cases do not prove coverage of every possible incident.

The [S3 evaluation path](../evaluations.md#s3-fresh-candidate-before-deployment) specifies later local captured-evidence execution and AgentCore on-demand scoring before deployment. S4/S5 reuse the execution function through Strands; their semantic evaluator backend remains open. The telemetry collector, evaluator adapters, case/evidence versioning, reference/result mapping, and release thresholds belong to the evaluation stages and still require implementation and verification. The initial live event/run record, report contract, model, tool bounds, IAM boundaries, source capture, Runtime finalization, and controller discovery are defined above. Python ZIP packaging is supported for the AgentCore Runtime artifact; the [deployment design](../deployment.md) records the GitHub Actions and CDK workflow. [AgentCore Python ZIP deployment](https://docs.aws.amazon.com/bedrock-agentcore/latest/devguide/runtime-get-started-code-deploy-python.html). The [demo script](../demo-script.md) and [talk plan](../talk-plan.md) own presenter sequence, timing, and live-edit steps; this component document specifies agent capability and behavior only.

The related [application](application.md) and [failure controller](failure-controller.md) documents describe evidence sources and fault/action boundaries. The application and controller use TypeScript; that choice does not select their runtime for the Python Strands agent or evaluation code.
