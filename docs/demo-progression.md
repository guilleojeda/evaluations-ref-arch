# Demo progression

The reference uses six capability checkpoints, S0–S5, that show how evidence about an agent becomes a release decision. They use the same two application incidents and the same reviewed cases throughout. The audience-facing section order, screen transitions, and overlapping waits belong to the [talk plan](talk-plan.md) and [demo cue sheet](demo-script.md); the checkpoints need not be presented as section titles or as one uninterrupted software-edit sequence. The [scenario contracts](demo-scenarios.md), [agent description](components/operations-agent.md), and [controller specification](components/failure-controller-behavior.md) define component behavior.

## Two independent dimensions

A checkpoint describes the evaluation capability shown on screen. A candidate describes the agent behavior being evaluated. Advancing a checkpoint does not repair a candidate: the original faulty candidate remains available through S2 and for comparison after the explicit prompt repair at S3. The repaired candidate continues through the developer experiment workflow at S4 and the release gate at S5.

The selected faulty behavior is concrete. At S0, during an Inventory access-denied incident, the candidate recommends increasing memory on the Inventory function. That setting change cannot remove the table-policy Deny. After the presenter applies it, separate ordinary traffic still shows the access-denied failure. The candidate need not be wrong on both incidents: the capacity case can have a correct recommendation even while this access-denied case exposes the defect.

## Checkpoints

| State | What appears in the talk | What the audience should conclude |
| --- | --- | --- |
| S0 — Instrumented agent | Run one genuine alarm-triggered, read-only investigation with the faulty prompt. The same four tools, report, tracing, and source capture are available; there are no evaluation cases, evaluators, scores, or gate. The agent chooses relevant queries, windows, and order from available evidence rather than receiving a preassembled packet. The faulty candidate recommends **Increase memory — INVENTORY — larger MB** for the access-denied incident. | The configuration readback confirms the memory/version setting change only. It does not prove an application effect; separate traffic still fails because access remains denied. |
| S1 — Agent with reviewed cases | Keep the unchanged faulty agent. Review the input and captured-evidence reference, define acceptable and unacceptable behavior, fully construct one reviewed case, then open the separately prepared case file. | Expectations and case meaning are reviewed before scoring; S1 produces no verdict. |
| S2 — Evaluated agent | Keep the same faulty agent. Add deterministic action/target checks plus semantic diagnosis and grounding criteria with judge configuration, and show AgentCore evaluation results. Both evaluator types are introduced here; the candidate remains faulty through S2. | The memory action fails the action check and the diagnosis/judgment explains why it is unsupported by the policy Deny. |
| S3 — Repaired candidate | Edit the prompt only. Keep the model, tools, permissions, and report behavior fixed. Execute the fresh candidate against the same cases and criteria and compare it with the original. A stage introduction does not imply that pending results have passed. | The prompt repair changes candidate behavior while incident, case expectations, and evaluation criteria remain fixed. |
| S4 — Agent with developer experiment workflow | Keep the same repaired candidate. Use the local Strands experiment entrypoint connecting the case, task, evaluator, report, and comparison. Evaluate the existing reviewed local release policy before the first deployment; deployment is an action, not another stage. | The developer workflow makes the experiment repeatable and produces the local evidence needed before deployment. |
| S5 — Agent with release gate | Keep the same repaired candidate. CI runs the same experiment and policy before deployment. Failed or incomplete required results block deployment. A prepared friend's prompt regression is another candidate evaluated here; there is no S6. | The release gate binds the decision to the candidate and blocks an unsupported release. |

The agent's proposal menu has exactly four choices: **Increase reserved concurrency** (select CHECKOUT or INVENTORY and a higher cap), **Increase memory** (select CHECKOUT or INVENTORY and a larger MB allocation), **Restore inventory access** (restore the expected Inventory table policy), or **Other** with a reason, including no change or unknown. The agent proposes exactly one choice. It has read-only investigation tools; the presenter independently chooses and executes any controller action. The agent has no automatic remediation path. Configuration actions do not generate application traffic or establish application health; their readbacks and later traffic evidence are separate facts.

## Evaluation workflow and evidence

S1 expectations come from reviewing the observed run, not copying the faulty answer into the case. At S2, deterministic checks test concrete trace facts, the proposed action, and target validity; the configured judge assesses diagnosis and grounding. Both evaluator types are introduced here. For numeric capacity and memory targets, accept more than one justified value within reviewed bounds; the initial memory example uses the correct INVENTORY target with the wrong action. S3 changes only the prompt and compares a fresh candidate execution with the original on the same cases and criteria; pending results remain pending. S4 connects the case, task, evaluator, report, and comparison in the local Strands experiment and evaluates the existing reviewed local release policy before the first deployment. S5 runs that same experiment and policy in CI and blocks deployment on failed or incomplete required results. Separately observed application outcomes establish what happened after each remedy.

Strands represents the in-code experiment workflow. AgentCore evaluates actual traces from both the deployed agent and the prepared local candidate runner. At S3, that runner executes the shared constructor with captured providers and submits its fresh telemetry for AgentCore on-demand scoring before deployment. S4 reuses the execution task in the full Strands experiment, whose semantic evaluator backend remains open. Preserve the same case meaning and criteria without claiming automatic format interchange or duplicating every evaluation. The distinction is workflow and trace context, not a division by evaluator type. See the [evaluation roles](evaluations.md#strands-and-agentcore-roles) and [S3 execution path](evaluations.md#s3-fresh-candidate-before-deployment).

Keep the same reviewed cases and versioned evidence views when comparing the identified faulty and repaired candidates. Local/CI Strands runs execute each candidate against queryable captured evidence for all four tools at the case's explicit reference time. Each candidate chooses its own queries; neither current recovered configuration nor future change history enters that view. Capture source evidence before recovery without creating a case or score at S0; review and case creation belong to S1. Prepare captured-provider/backend plumbing before the talk. Each regression execution has a new identity while retaining original event/case provenance. Label a saved trace as recorded: rejudging it assesses that recorded execution and cannot establish that a changed candidate was executed. See the [evaluation contract](evaluations.md).

At S5, the CI release gate evaluates the pending candidate before deployment and binds its result to that source and agent artifact identity. Existing deployed-agent traces can supply genuine AgentCore examples, but cannot stand in for execution of the repaired candidate. One shared development environment remains sufficient.

## Checkpoint and session preparation

Presentation cues and live edits belong in the [demo script](demo-script.md) and [talk plan](talk-plan.md). Prepare infrastructure, real alarm delivery, evaluation integrations, results, and any CI wiring before the session. Live edits should show the lesson rather than build that plumbing. The sequence is a teaching progression, not a claim that the checkpoints or agent already exist. Captured-provider and backend plumbing must be prepared before the talk.

Before each session, select the intended candidate and checkpoint, stop traffic, settle outstanding work, restore healthy aliases and baseline memory/version/capacity/policy settings, and verify normal application behavior. A non-destructive recovery retains business data; a full reset follows the scenario contract's product-version and order/stock semantics. Observe the actual alarm OK before a new alarm-driven incident, then match the resulting event to its agent run. Do not substitute a manual invocation. The December 1 and December 3 sessions each start from a verified baseline rather than leftover incident state.

Confirm the controller baseline belongs to the currently deployed generation. An automatic deployment has priority over controller work and suspends operation through the handoff; the presenter reconciles and verifies a new baseline afterward before resuming traffic. Existing run history and consumed budgets remain. This is development behavior, not an additional talk checkpoint; see [deployment](deployment.md#deployment-and-controller-baseline).

After the S0 **Recover**, the live fault has ended. Later regression executions use the reviewed incident's captured evidence at its explicit investigation reference time; they do not query the recovered application as though it were still failing. A stale-alert case uses a separately identified later reference time and captured post-recovery evidence. An earlier report did not know the future. The dashboard retains the originating ALARM identity through OK and discovers the matching durable run even after missed polls. A fresh corrected live run requires a newly observed alarm **OK**, a new incident, and its own matching event/run; memory changes or Recover do not trigger an agent run. When evidence at the investigation reference time supports no change, **Other** with a reason is a valid recommendation.
