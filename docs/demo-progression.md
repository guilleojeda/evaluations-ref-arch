# Demo progression

The talk presents five checkpoints, S0–S4, that show how evidence about an agent becomes a release decision. They use the same two application incidents and the same reviewed cases throughout. This is a presentation sequence; the [scenario contracts](demo-scenarios.md), [agent description](components/operations-agent.md), and [controller specification](components/failure-controller-behavior.md) define component behavior.

## Two independent dimensions

A checkpoint describes the evaluation capability shown on screen. A candidate describes the agent behavior being evaluated. Advancing a checkpoint does not repair a candidate: the original faulty candidate remains available at S4 so the audience can see the same cases fail before and pass after an explicit repair.

The selected faulty behavior is concrete. At S0, during an Inventory access-denied incident, the candidate recommends increasing memory on the Inventory function. That setting change cannot remove the table-policy Deny. After the presenter applies it, separate ordinary traffic still shows the access-denied failure. The candidate need not be wrong on both incidents: the capacity case can have a correct recommendation even while this access-denied case exposes the defect.

## Checkpoints

| State | What appears in the talk | What the audience should conclude |
| --- | --- | --- |
| S0 — One investigation | One real alarm-triggered, read-only investigation and report; no chat loop, evaluation case, score, or gate. The agent chooses relevant queries, time windows, and their order from available evidence rather than receiving a preassembled incident packet. The faulty candidate recommends **Increase memory — INVENTORY — larger MB** for the access-denied incident. The presenter applies that action independently and then generates separate ordinary traffic. | The configuration readback confirms the memory/version setting change only. It does not prove an application effect; the later request still fails because access remains denied. |
| S1 — Reviewed expectations | Review the captured run and queryable source evidence; create a versioned case with an explicit investigation reference time, expected diagnosis, evidence, and one allowed action/target. | Expectations are reviewed before scoring. S1 produces no evaluation verdict. |
| S2 — Deterministic behavior checks | Run deterministic checks against the reviewed case. For the opening memory example, the INVENTORY target is correct but the memory action is wrong because it cannot remove the policy Deny. Separate wrong-target proposals also fail their target checks; accept any justified numeric target within the reviewed bounds. | A check can distinguish an incorrect action from an incorrect target without interpreting prose or enforcing one arbitrary value. |
| S3 — Evidence and diagnosis judgment | Add a semantic criterion for evidence use, diagnosis, and whether the proposal follows from the evidence. Run a genuine AgentCore evaluation on the captured trace alongside the Strands workflow. | The proposal is unsupported because memory cannot remove the observed policy Deny. Evaluation reports the defect; it does not repair the candidate or remediate the application. |
| S4 — Explicit repair and release decision | Repair the candidate explicitly, then compare faulty and repaired candidates on the identical reviewed cases. Keep the faulty candidate runnable. Show the capacity case recommending increased reserved concurrency for INVENTORY and the access-denied case recommending restoration of the expected Inventory policy. Include separate observed remedy outcomes: repeat comparable delivered capacity demand at the raised cap, and ordinary reads after policy restoration. Use clearly labeled actual saved executions when live time is short. Apply the selected release policy to evaluation findings, separately from observed application effects. | The repair changes the agent behavior, not the incident or case expectations. Both correct recommendations and their application effects have actual evidence; an evaluation result alone does not establish recovery. |

The agent's proposal menu has exactly four choices: **Increase reserved concurrency** (select CHECKOUT or INVENTORY and a higher cap), **Increase memory** (select CHECKOUT or INVENTORY and a larger MB allocation), **Restore inventory access** (restore the expected Inventory table policy), or **Other** with a reason, including no change or unknown. The agent proposes exactly one choice. It has read-only investigation tools; the presenter independently chooses and executes any controller action. The agent has no automatic remediation path. Configuration actions do not generate application traffic or establish application health; their readbacks and later traffic evidence are separate facts.

## Evaluation workflow and evidence

S1 expectations come from reviewing the observed run, not copying the faulty answer into the case. At S2, deterministic checks test concrete trace facts, the proposed action, and target validity. For numeric capacity and memory targets, accept more than one justified value within reviewed bounds; the initial memory example uses the correct INVENTORY target with the wrong action. At S3, semantic judgment assesses whether the diagnosis and proposal are grounded in the available evidence. At S4, the release policy consumes the required results, including incomplete or unavailable evaluations; separately observed application outcomes establish what happened after each remedy.

Strands represents the in-code experiment workflow. AgentCore demonstrates evaluation of a deployed agent trace. The distinction is workflow and trace context, not deterministic checks versus model judgment; evaluator placement remains open, and the talk does not duplicate every evaluation in both systems. See [evaluation approach](evaluations.md#strands-and-agentcore-roles).

Keep the same reviewed cases and versioned evidence views when comparing the identified faulty and repaired candidates. Local/CI Strands runs execute each candidate against queryable captured evidence for all four tools at the case's explicit reference time. Each candidate chooses its own queries; neither current recovered configuration nor future change history enters that view. Capture source evidence before recovery without creating a case or score at S0; review and case creation belong to S1. Each regression execution has a new identity while retaining original event/case provenance. Label a saved trace as recorded: rejudging it assesses that recorded execution and cannot establish that a changed candidate was executed. See the [evaluation contract](evaluations.md).

At S4, the local/CI gate evaluates the pending candidate before deployment and binds its result to that source and agent artifact identity. Existing deployed-agent traces can supply genuine AgentCore examples, but cannot stand in for execution of the repaired candidate. One shared development environment remains sufficient.

## Checkpoint and session preparation

Presentation cues and live edits belong in the [demo script](demo-script.md) and [talk plan](talk-plan.md). Prepare infrastructure, real alarm delivery, evaluation integrations, results, and any CI wiring before the session. Live edits should show the lesson rather than build that plumbing. The sequence is a teaching progression, not a claim that the checkpoints or agent already exist.

Before each session, select the intended candidate and checkpoint, stop traffic, settle outstanding work, restore healthy aliases and baseline memory/version/capacity/policy settings, and verify normal application behavior. A non-destructive recovery retains business data; a full reset follows the scenario contract's product-version and order/stock semantics. Observe the actual alarm OK before a new alarm-driven incident, then match the resulting event to its agent run. Do not substitute a manual invocation. The December 1 and December 3 sessions each start from a verified baseline rather than leftover incident state.

Confirm the controller baseline belongs to the currently deployed generation. An automatic deployment has priority over controller work and suspends operation through the handoff; the presenter reconciles and verifies a new baseline afterward before resuming traffic. Existing run history and consumed budgets remain. This is development behavior, not an additional talk checkpoint; see [deployment](deployment.md#deployment-and-controller-baseline).

After the S0 **Recover**, the live fault has ended. Later regression executions use the reviewed incident's captured evidence at its explicit investigation reference time; they do not query the recovered application as though it were still failing. A stale-alert case uses a separately identified later reference time and captured post-recovery evidence. An earlier report did not know the future. The dashboard retains the originating ALARM identity through OK and discovers the matching durable run even after missed polls. A fresh corrected live run requires a newly observed alarm **OK**, a new incident, and its own matching event/run; memory changes or Recover do not trigger an agent run. When evidence at the investigation reference time supports no change, **Other** with a reason is a valid recommendation.
